# タスクと状態

プロジェクトとタスクの構造、有効なレーンと稼働状態の組み合わせ、エピック・下書き・アーカイブとの関係を説明します。各項目の詳細は[共有ファイル](../reference/files.md)にあります。

## プロジェクト

プロジェクトは、名前と不変な**ProjectId**（作成時に生成する32桁の小文字16進文字列）を持つ作業単位です。各プロジェクトはカンバンを一つだけ持ちます。プロジェクト横断のカンバンや、プロジェクト間のタスクの移動・コピーはありません。

- 名前は前後の空白を除いて1〜50 Unicodeスカラー値、1行で、大文字・小文字を区別した完全一致で一意です。プロジェクト一覧は名前順です。
- 名前変更と`init`ではProjectIdは変わりません。削除したProjectIdは再利用しないので、同じ名前で作り直したプロジェクトは別のプロジェクトです。
- タスクID・レーン内のposition・EPIC-IDはプロジェクト内の値です。対象のプロジェクトを、省略・作業フォルダ・Webの選択から推測しません。
- `nextTaskId`は1から始まり、削除や`init`の後もリセットされず、増え続けます。作成に失敗した場合も、予約済みの番号は再利用しません。
- `init`はID・名前・`nextTaskId`を保ち、タスクとエピックを空にします。プロジェクトの削除はそのフォルダ全体を消し、ほかのプロジェクトには触れません。

変更の検知には三つの値を使います。`version`は1プロジェクトの正本ファイルから計算し、順序を持ちません。`catalogVersion`は、同じ方法でプロジェクト一覧の変更を識別します。`cursor`（`f1:<ProjectId>:<version>`）は`wait`が使う値で、名前変更後も同じProjectIdを追い、別のプロジェクトへは移りません。

## レーンと稼働状態

レーンは作業がどこにあるかを、稼働状態はエージェントがそれに対して何をしているかを表します。有効な組み合わせは限られます。

| 担当 | レーン | 有効な稼働状態 |
| --- | --- | --- |
| ai | backlog | idleのみ |
| ai | todo | idleのみ |
| ai | doing | idle、running、paused |
| ai | done | idleのみ |
| human | すべて（backlogを含む） | idleのみ |

- **Idle**は、エージェントが作業していないタスクです。**Running**は自己申告で、生存監視ではありません。自動では戻りません。ただし、エージェントの接続で稼働させたタスクは、その接続がしばらく動きのないまま続いたとき、置き換えられたとき、セッションとともに終わったときに稼働待に戻ります。エージェントもセッションが始まったというだけでは変えません。**Paused**（`paused`）は、稼働が止まっている、Doingのタスクです。質問を出したか結び付けたとき、常駐エージェントがエラーで止まったとき、人が一時停止したとき、または止まり検知のリマインダーに指摘されたエージェントが、作業していない自分のRunningのタスクを一時停止したときにPausedになります。エージェントがそれ以外で`state <id> paused`を使うことはありません。
- `running`と`paused`があるのは、DoingにあるAI担当のタスクだけで、ほかのタスクはすべて`idle`です。`task.json`に保存するのは`idle`・`running`・`paused`のどれかで、`ran`や`awaiting_answer`を含むそれ以外の値は、未知の値と同じく不正なファイルになります。
- **Awaiting answer**（回答待）は稼働状態ではなく、導き出す印`awaitingAnswer`です。タスクが参照するプロジェクトの質問にまだ回答がない場合、または読めないメッセージのファイルを参照している場合に真になります。担当者、レーン（バックログとDoneを含む）、稼働状態を問わず付き、アーカイブ済みのタスクは対象外です。`agentStatus`を上書きすることはなく、読み出すときにタスクの`questions`から導き（[メッセージ](./history-and-decisions.md#メッセージ)）、画面では稼働状態のラベルの上に表示します。その間もほかのタスクを進めてかまいません。
- 無効な組み合わせは保存しません。下書きのタスクは、どのレーンでもIdleです。

操作によって状態は次のように変わります。

- **作成**はタスクを未着手・Idleでレーンの末尾に置き、作成を履歴に記録します。本文がなければ空の`acceptance`と空の本文を書き、指定した本文はfrontmatterの検証を通します。
- **列移動**は`actor`が必須で、`reason`は任意です。タスクは移動先のレーンの末尾に置きます。実際の移動ではタスクの未回答の質問を保ち、Doingに入るとき、またはDoingから出るとき（どのレーンへでも）は稼働状態をIdleに戻すので、Doingに移したタスクはIdleから始まります。すでにDoingにあって並べ替えだけのタスクは状態を保ちます。実際の移動は履歴を追加し、`taskStatusChangedAt`を更新します。同じレーンへの移動は何も変えません。自動DoneもIdleにします。
- **稼働状態の変更**は`actor`が必須で、レーンは変わりません。`state`はDoingにあるAI担当のタスクに使います。許されるのは、IdleからRunning、RunningからPaused、PausedからRunningの変更だけで、それ以外（たとえばRunningからIdle、IdleからPaused）は`invalid_state_change`で拒否します。`idle`・`running`・`paused`以外の値（`ran`や`awaiting_answer`など）は`invalid_value`で拒否します。エージェントは自分のRunningのタスクを、止めた理由を`--reason`に書いてPausedにできます。スキルが使うよう指示するのは止まり検知のリマインダーのときだけで、再開は`state <id> running`です。回答待ちのタスクをAIがRunningにしようとすると`questions_unanswered`で拒否します。質問は`message ask`で出し、そのときDoingのRunningのタスクは同じ保存でPausedになります。`message link`でタスクを結び付けるときも同じです（[メッセージ](./history-and-decisions.md#メッセージ)）。列移動やアーカイブをしても、タスクの質問と参照は残ります。同じ状態の再申告は変更ではありません。
- **自動再開。** エージェントが回答を受け取ると（`message accept <Q-id> --actor ai`、または回答済みの結果を返す`message ask`と`message wait`。この2つは回答を受け取ります）、その質問を参照し、Pausedで、下書きでなく、ほかに未回答の質問を参照していない、DoingのAI担当のタスクは、同じ保存でRunningに戻ります。履歴には、プロダクトが作る言語に合わせた定型文「Q-1 の回答を受け取ったので再開しました。」を残します（IDが複数のときは「, 」で並べます）。質問によるPausedの履歴は「Q-1 の回答を待ちます。」です。
- **DoingからTodoへの差し戻し。** エージェントはDoingのタスクをTodoに戻せません。DoingのタスクへのAIの`mv <id> todo --actor ai`は`human_only`（「moving a task from Doing back to Todo is for a person only.」）で拒否します。戻せるのは人です。エージェントはタスクをDoneに移して終えます。
- **編集**で変わるのはタイトル・本文・完了条件だけで、担当は変わりません。CLIの`--desc`・`--desc-file`はファイル全体を受け取りますが、保存済みの最新の`TASK.md`の履歴と`questions`の参照を保ちます。入力のこの2つのキーは無視されるため、未回答の質問を参照するタスクは回答待のままです。`epic edit --document-file`は`EPIC.md`の全文を置き換えます。Web画面は`body`と`acceptance`を送り、ロックの中で最新のファイルに適用します。
- **エピックの所属**は`epicId`を設定または解除します。実際に変わったときだけ履歴を追加します。下書きやアーカイブ済みのタスクでも人は変更できます。
- **削除**はタスクのフォルダを消します。Web画面はアーカイブ済みのタスクだけを削除し、CLIは端末での確認を求めます。

通常の更新では、後から保存した内容が優先され、内容の照合や編集ロックはありません。最新の`task.json`と照らして書き込みロックの中で検証するのは、回答、人の下書きへのAIの書き込み、アーカイブ済みへの書き込み、一括アーカイブの対象だけです。

## エピックとウェーブ

エピックは、タスクをまとめて進行と作業順を管理する単位です。エピックの詳細（`EPIC.md`）には、目的・範囲・判断などをMarkdownで書きます。タスクは最大で一つのエピックに所属でき、所属の正本はタスクの`epicId`だけです。エピック側はタスクの一覧を保存しません。

| 項目 | 規則 |
| --- | --- |
| `id` | EPIC-ID。`[A-Z][A-Z0-9]*(?:-[A-Z0-9]+)*`に合う1〜64文字。小文字の入力は大文字にする。変更不可。 |
| `name` | 前後の空白を除いて1〜100文字、1行。 |
| `color` | `#RRGGBB`（大文字）。省略時は作成時に乱数で決める。 |
| `draft` | タスクと同じく`null`または`"human"`。人の下書き（`human`）のエピックは、CLIの`epic edit`と`--waves`を`epic_is_draft`で拒否する。所属タスクと`epic attachment`には影響しない。エピックにレーンはなく、`progress`には任意の`backlog`の件数がある。 |
| `document`・`body` | frontmatterを含む`EPIC.md`の全文（0〜100,000文字）と、frontmatterを除いた本文。 |
| `waves`・`wavesError` | 所属タスクの作業順をウェーブ（タスクIDのリストのリスト）で表したものと、保存された順序の読み込みに失敗したかどうか。 |

- タスクは`epicId`だけを保存し、ラベルの色と名前は取得時に解決します。
- アーカイブ済みを含め、いずれかのタスクが参照しているエピックは削除できません（`epic_in_use`）。Web画面ではエピックの編集画面から`DELETE .../epics/{epicId}`で削除します。CLIでは`epic rm`を使います。
- 新しいプロジェクトには、既定のエピック`BUG`と`ENHANCEMENT`が最初からあります。どちらも通常のエピックなので、編集も削除もできます。プロジェクトにこれらを用意し終えると`project.json`の`defaultEpicsSeeded`が設定されるので、削除した既定のエピックが作り直されることはありません。`serve`は、このフラグがまだないプロジェクトに一度だけ用意します。
- エピックには管理対象の完了条件はありません。参考条件は本文の通常のMarkdownで、APIはエピックへの`acceptance`の入力を拒否します。
- `waves`は`EPIC.md`のfrontmatterにあるYAMLのリストで、各項目が1つのウェーブです。項目はタスクID（`24`）、またはカンマでつないだタスクID（`26,25`。カンマの後の空白と引用符は許容）です。入れ子のリストは受け付けません。ウェーブをまたぐ重複、正でないID、空の項目、型の誤りはエラーです。保存時は、空のウェーブを取り除きます。所属しなくなったIDは表示から除き、次の保存で取り除き、空になったウェーブも取り除きます。記載のない所属タスクは作成順で後に続きます。ウェーブの変更はDoneのタスクの編集に当たりません。レーン内の`position`は、エピックの作業順序には影響しません。
- ウェーブは、その前のウェーブのタスクがすべてDoneになってから始まります。`nextTasks`は、同じエピックの前のウェーブに、アーカイブされておらずDoneでないタスクが残っている間、その未着手のタスクを載せません。アーカイブしたタスクは無視し、どのウェーブにも載らないタスクは待たされず、順序を読めないときは何も止めません。止まっているDoingの作業は、これまでどおり`resume`として載ります。

## 下書き

下書きは、人がまだ書いているタスクやエピックです。`draft`は`null`（通常のタスク）か`"human"`（人がブラウザで書いている。編集ロック）です。保存される項目は[共有ファイル](../reference/files.md)にあります。下書きに期限はなく、`wait`と自動Doneはすべての下書きを飛ばします。AIの下書きはありません。エージェントが提案する計画はバックログのタスクです（[バックログと送信](#バックログと送信)を参照）。

- エージェントが作ったタスクとエピック（CLIの`add`と`epic add`）は`draft: null`です。人が作ったものは`null`で、ブラウザで下書きとして作ると`human`です。
- プレビューは、最初の実際の変更で人の下書きに入ります。タスクは`PUT /tasks/{id}/draft`で`draft: "human"`を送り、エピックは`PATCH /epics/{id}`で`draft: "human"`を送ります。下書きにできるのはRunningでないタスクだけで、Runningは`invalid_state_for_draft`で拒否します。実際の変更は履歴を追加しますが、`updatedAt`は変えません。エピックの下書きに入る・出るときも`updatedAt`は変わりません。古いバージョンのクライアントが送る`draft: "ai"`は受け付け、`null`として扱います（編集ロックを解除します）。`draft: "ai"`でのタスクの作成は拒否します。
- `human`の下書きでは、CLIの`edit`・`mv`・`state`・`history add`が書き込みロックの中で`draft`を確かめ、`task_is_draft`で失敗し、CLIの`epic edit`と`epic edit --waves`は`epic_is_draft`で失敗します。読み取り、`add`、`epic attachment`、所属の変更には影響しません。エピックへのWebの`PATCH`は下書きを拒否しません。
- Webの編集は下書きのタスクだけを受け付けます。`finalize`を指定すると、本文・タイトル・`draft: null`・履歴を一組で確定します。破棄は、`draft: null`と`discard: true`を送り、履歴に`Discarded draft changes.`を残します。エピックに履歴はないので、破棄は`PATCH /epics/{id}`の`draft: null`だけです。
- 下書きの`TASK.md`の直接編集は製品では止められず、READMEとエージェントのスキルで編集しないよう伝えます。

## バックログと送信

バックログのレーンは、まだ始めてはいけない確定済みの計画を置く場所で、「始めない」と同じ意味です。計画はチャットやAIへの依頼で直します。バックログ専用の編集はなく、通常のカードの編集は変わりません。バックログを使う`epic.json`は`formatVersion: 2`になります。`task.json`は、バックログを使うかどうかにかかわらず`formatVersion: 3`です（[保存と復旧](./saving-and-recovery.md#形式のバージョンとdraftの値)を参照）。

- **作成。** `agpj add ... --actor ai --backlog`でバックログにカードを作ります。エージェントは、計画だけを頼まれたときに使います。`--backlog`なしのエージェントの`add`は、通常の未着手のタスクを作ります（未回答の質問があればこれまでどおりAwaiting answerになります）。`epic add`にレーンはありません。エージェントのエピックは通常のエピックで、計画だけのエピックは、カードを`--backlog --epic <ID>`で作ったものです。
- **送信。** バックログから未着手へは、人か、ユーザーに指示されたエージェントが送ります。1枚のカードには`agpj mv <id> todo --actor human|ai [--force]`（`send`という別のコマンドはありません）、エピック全体または選んだカードを、全部成功か何も変えないかの一回の保存で送る`agpj epic send <EPIC-ID> --actor human|ai [--tasks 1,2] [--force] [--reason TEXT]`です。Webのルートは`POST /tasks/{id}/send`と`POST /epics/{epicId}/send`（[Web API](../reference/web-api.md)を参照）で、WebのUIではバックログのレーン、カードの詳細、エピックの詳細から送れます（[サーバーとUI](./server-and-ui.md)を参照）。Skillは、エージェントがユーザーに指示されたときだけ送り、そのことを`--reason`に記録するよう求めます。エージェントの`--force`は`human_only`になります。未着手へ送ったカードは未着手の末尾に置かれます。`mv`がこの規則を使うのは、カードをバックログから未着手へ移すときだけです。すでにバックログを出たカードはほかのカードと同じように移り、送信のルートでは何も変わらないので、再試行しても安全です。人が編集中のカード（`draft: human`）は送れません（`task_is_draft`）。履歴には`人が Todo へ送りました。`または`エージェントが Todo へ送りました。`と残り、`--reason`があれば続けて入ります。
- **未回答の質問。** 未回答の質問がある計画は、人が`--force`（CLI）または`ack: true`（API）で確認するまで、`send_with_open_questions`（409。メッセージに質問のIDを示す）で拒否します。送ったあとも質問は残り、回答があるまでカードはAwaiting answerです。Awaiting answerはバックログでも付くので、未回答の質問がある計画は送る前からこの印が付いています。
- **移動。** エージェントのバックログのカードへの`mv`・`state`は`task_in_backlog`で失敗します。人によるCLIやWebでの未着手への移動は送信で、DoingやDoneへの移動も人なら行え、送信と同じ規則に従います（未回答の質問には`--force`または`ack`が要り、編集中のカードは拒否されます）。エージェントがバックログのカードをDoingやDoneへ動かすことはなく、バックログを出る道は送信だけです。`agpj mv <id> backlog --actor human`は、未着手の未着手のカード（Idleで成果なし）をバックログへ戻します。エージェントが行うと`human_only`です。
- **エージェントの画面。** nextTasks・`wait`・Hook・常駐セッション・自動Done・進捗表の候補は、バックログを見ません。エピックの中のバックログのカードは、Doneではないので、あとのウェーブを待たせ続けます。エピックの`progress`には、任意の`backlog`の件数があり、0のときは省きます。
- **規則の置き場所。** 送信の規則は`src/file_store/ops/send.rs`にあり、CLIの`mv <id> todo`とWebの送信ルートはどちらも`send_task_locked`に行き着きます。`check_sender`と`open_questions`が、タスク、またはエピックの送信が動かすすべてのカードについて、エージェントと、確認のない未回答の質問のある計画を拒みます。
- 下書きの`TASK.md`の直接編集は製品では止められず、READMEとエージェントのスキルで編集しないよう伝えます。

## アーカイブ

- アーカイブでは、レーン・`draft`・`epicId`・positionを保ち、稼働状態は`idle`にし、質問の参照を保ち、`updatedAt`を更新します。レーンと`taskStatusChangedAt`は変わりません。Web画面のアーカイブと復元は、固定の理由`Archived by user.`と`Restored by user.`を記録します。
- 復元したタスクは、アーカイブしたときのレーンの末尾に置きます。稼働状態は`idle`のままなので、レーンと状態の組み合わせは常に作業モデルで有効です。スマホのアーカイブ一覧も、PCと同じ`POST …/tasks/{id}/restore`で復元します。
- 通常のスナップショット・`ls`・Hookは未アーカイブのタスクだけを返し、`show ID`はアーカイブ済みも表示します。アーカイブ済みへの書き込みは`task_archived`で失敗しますが、画像は読めます。アーカイブ一覧は`archivedAt`の新しい順で、同じ時刻ならタスクIDの大きいほうが先、読み取れる`archivedAt`のないタスクは最後です。`GET …/archive`は`sort_archived_newest_first`（`src/file_store/reader/snapshot.rs`）で並べ、Web UIも`sortArchivedNewestFirst`（`web/src/features/tasks/api/read.ts`）で同じ順に並べ直すため、PCの一覧とスマートフォンの一覧は同じ順序になります。

## リリース予定のバージョン

プロジェクトはファイルとしてバージョンの一覧を持ち、そのうち1つをリリースバージョンにでき、タスクは1つのバージョンを予定として持てます。予定は任意で、予定のないタスクは予定がないままです。バージョンは、プロジェクトのDocsの`docs/release/`直下にある`*.md`ファイルです。プロジェクトは`project.json`に`releaseVersion`を、各タスクは`TASK.md`のフロントマターに`plannedVersion`を持ちます。配置、並び順、バージョンの名前の形式は[リリース予定のバージョン](../reference/files.md#planned-versions)を参照してください。

- 各タスクの予定のバージョン、つまり`TASK.md`の`plannedVersion`キーが正で、人が手で編集することもできます。タスクごとにも、エピックの全タスクへまとめてでも設定でき、1つのエピックに異なるバージョンのタスクが混在できます。
- リリースバージョンを割り当てると、その時点のバージョンの名前を保存します。あとでプロジェクトのリリースバージョンを変えても、タスクは動きません。
- 変更は、同じ保存で通常の履歴エントリを1件追加し、前後のバージョンと時刻を記録するので、あとから「どのタスクがいつバージョンから外れたか」を読めます。すでにあるバージョンを設定し直しても何も変わらないため、再試行でエントリは増えません。
- 操作（`set_task_planned_version`・`set_epic_planned_version`・`add_version`・`set_release_version`）は、他の書き込みと同じくプロジェクトの書き込みロックの下で動きます。バージョンの設定で担当者・レーン・稼働状態・位置・完了条件が変わることはありません。DoneまたはアーカイブされたタスクでもAIと人のどちらも設定できる、唯一開いたままの項目です（Doneのタスクのそのほかの編集はエージェントには読み取り専用のままで、Doneのタスクでバージョンの変更とほかの変更を組み合わせた編集は全体が拒否されます）。AIは人の下書きを変更できません。エピック一括の操作は、アーカイブ済みとDoneのタスクを引き続きスキップします。
- Summaryは`project.versions`、`project.releaseVersion`、各タスクの`plannedVersion`を持ちます（[Web API](../reference/web-api.md#summaryとdetail)を参照）。バージョンのファイルを手で追加・削除したり、`TASK.md`の`plannedVersion`を編集したりしても、ほかのファイルの変更と同じようにカンバンへ届きます。

## 並び順と日時

- PCのカンバンとCLIでは、未着手と進行中はpositionの昇順、Doneはpositionの降順です。モバイルのDone一覧は`taskStatusChangedAt`の新しい順です。完了順を履歴から推測しません。APIの`tasks`はID順で、画面が表示用に並べ替えます。エピックはEPIC-ID順です。
- 保存とJSONの日時は、厳密に`YYYY-MM-DDTHH:MM:SSZ`の形のUTC文字列です。時差表記（`+00:00`も）と小数秒は拒否します。表示は`MM/DD HH:mm`で、CLIは実行環境、画面はブラウザのローカル時刻を使います。
